# Задание 4.1 (часть 3) — Исследовательское тестирование

**Вид тестирования:** exploratory (исследовательское) + ad-hoc, без заранее
написанных чек-листа и тест-кейсов.
**Дата и время:** 22.11.2026, 14:10–15:20 (2 сессии × 35 мин, таймбокс соблюдён)
**Тестировщик:** Кондрашев Никита
**Объект:** «БРИТВА» — путь записи клиента
**Окружение:** Windows 11, Chrome 157, `frontend-4-practice` →
`http://localhost:3000` (Vite 8.2.1, API-заглушка `server/database.js`)
**Эталон:** макет Figma «БРИТВА — путь записи клиента», 6 основных экранов
(01 Главная, 02 Услуги, 03 Мастер, 04 Дата и время, 05 Подтверждение, 06 Успех)
и 3 альтернативных (ошибка телефона, слот занят, ошибка сети).

**Зачем эта сессия.** Матрица покрытия (часть 2) показывает 68 из 68
требований покрытыми тестами. Но требование, сформулированное неправильно
или не сформулированное вовсе, в матрице не видно: тест на него не напишут.
Поэтому после формального прогона проведена сессия без артефактов —
с единственной целью: найти то, чего нет в списке требований.
Результат — 4 дефекта, 13 новых требований и 9 новых тест-кейсов.

---

## 1. Чартер (миссия сессии)

> **Сессия 1.** Исследуем переходы между шагами записи и состояния кнопок,
> чтобы найти места, где пользователь не может пройти сценарий до конца
> или где индикатор шагов не совпадает с макетом. 35 минут.
>
> **Сессия 2.** Исследуем данные, которые интерфейс показывает пользователю
> (дата «сегодня», цена, адрес, детали записи), чтобы найти расхождения
> с макетом и с реальным календарём. 35 минут.

## 2. Правила сессии

1. Ничего не пишем в код во время сессии — только наблюдаем и фиксируем.
2. Каждое наблюдение записываем сразу, с временем: даже если кажется мелочью.
3. Любую цифру на экране сверяем с ответом API (вкладка Network / `fetch` из консоли).
4. Экран сверяем с макетом Figma, а не с памятью о макете.
5. Если находка воспроизводится — фиксируем шаги; если нет — помечаем «не воспроизвелось».

**Главный вывод.** Формальные тесты (37 пунктов чек-листа и 31 тест-кейс)
прогон прошли: дефектов они не находили, потому что проверяли только те
требования, которые кто-то успел записать. Все четыре новых дефекта лежат
за границей списка требований — там, где требование не сформулировано или
отличается от макета. Значит, критерий «все требования покрыты на 100%»
не равен критерию «продукт готов»: список требований сам нуждается в проверке.

## 7. Приёмы, которые использовались

- **Сверка с эталоном** — каждый экран сравнивался с макетом Figma, а не с
  собственной памятью о макете (так найдены BUG-011 и BUG-012).
- **Граничные значения** — «сегодня» сервера против системной даты (BUG-010).
- **Чтение данных мимо интерфейса** — прямые запросы к `/api/booking/today`
  и `/api/slots` из консоли: интерфейс показывал одно, API отвечал другим набором.
- **Проверка «а что если»** — повторное нажатие, снятие выбора, быстрые клики
  по дням (BUG-009).
- **Просмотр DevTools** — атрибуты кнопки и обработчики (причина BUG-009).

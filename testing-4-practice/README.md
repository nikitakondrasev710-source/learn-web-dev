### 0.1 Smoke-проверка (7 пунктов)

Выполняется перед полным тестированием, занимает 10–15 минут.

| № | Проверка | Ожидаемый результат |

| SM-1 | Страница открывается, консоль браузера | Страница отрисована, ошибок в консоли нет |
| SM-2 | Шапка и подвал | Логотип, 4 пункта меню, телефон `tel:`, кнопка «Войти», копирайт |
| SM-3 | Индикатор шагов | Три шага, текущий «Дата и время» выделен |

SM-2…SM-6 — дефект фиксируется, полное тестирование продолжается,
если сломанный блок не блокирует остальные проверки.

### 3.6 Роли, процесс и общение

В команде без выделенного аналитика тестировщик отвечает за снятие
неоднозначностей и поддержание процесса качества.

| Роль | Кто в учебном проекте | Что делал |
|---|---|---|
| Проектировщик | автор макета Figma | макет на 6 экранов и 3 альтернативных, определение шагов записи |
| Фронтенд | `frontend-1…4` | вёрстка → нативный JS → React → React + сервер |
| Бэкенд | `backend-1…4` | Python → FastAPI → SQLAlchemy/Alembic → Pydantic |
| **QA** | Кондрашев Никита | тест-план, чек-лист, тест-кейсы, баг-репорты, матрица покрытия, реестр неоднозначностей, отчёт |

**Процесс на фиче «выбор мастера»:**

1. Проектировщик приносит обновлённый макет: экран 03 «Мастер»
   и четвёртый шаг в индикаторе.
2. QA сверяет макет со списком требований, фиксирует неоднозначность
   **AMB-01** (три шага или четыре).
3. Трактовка согласуется: макет — эталон. В требованиях появляются
   REQ-69…REQ-72.
4. В матрице покрытия у новых требований тестов нет.
5. QA пишет тест-кейсы TC-32…TC-34, проводит прогон, оформляет BUG-012.
6. Дефект остаётся открытым и входит в отчёт с приоритетом Critical.

**О чём договорились:**

| Ситуация | Что делаем |
|---|---|
| Требование можно понять двояко | пишем в список AMB и сразу предлагаем трактовку |
| Поменялся макет или API | одно короткое сообщение в чат со ссылкой |
| Нашли дефект | баг-репорт BUG-NN плюс строка в сводке |
| Дефект починили | ретест, статус «Исправлен, проверен», номер теста |
| Прогон закончился | обновить статусы и сдать короткий отчёт |

## 7. Рекомендации

1. **Убрать захардкоженные даты.** Сейчас «сегодня» фиксировано
   (`2026-11-19`) — на реальной дате тесты будут падать.
   Нужно брать `new Date()` или данные с сервера.
2. **Добавить блокировку на уровне БД** при создании записи
   (BUG-008) — `SELECT ... FOR UPDATE` или уникальный индекс
   на `(master_id, starts_at)`.
3. **Покрыть автотестами UI** — Playwright или Cypress для сценария
   записи целиком, а не только API.
4. **Добавить CI** — GitHub Actions: линтер, тесты API, валидатор HTML
   на каждый push.
5. **Проверить на реальных устройствах** — iOS Safari, Android Chrome,
   так как сейчас адаптивность проверена только эмуляцией.
6. **Автоматизировать визуальную сверку с макетом** (скриншот-тесты):
   макет уже есть, не хватает именно автоматизации.
7. **Сверять список требований с макетом до прогона.** Ни одно из
   13 требований макета не попало в исходный список — там же находятся
   все четыре новых дефекта.
8. **Брать «сегодня» из системной даты** (BUG-010): календарь
   открывается на октябре 2026 при текущей дате 22.11.2026.
9. **Считать сумму из выбранной услуги** (BUG-011), а не хранить

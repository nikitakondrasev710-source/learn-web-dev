## 0. Вход в тестирование, критерии завершения и структура отчёта

### 0.1 Smoke-проверка (7 пунктов)

Выполняется перед полным тестированием, занимает 10–15 минут.

| № | Проверка | Ожидаемый результат |
|---|---|---|
| SM-1 | Страница открывается, консоль браузера | Страница отрисована, ошибок в консоли нет |
| SM-2 | Шапка и подвал | Логотип, 4 пункта меню, телефон `tel:`, кнопка «Войти», копирайт |
| SM-3 | Индикатор шагов | Три шага, текущий «Дата и время» выделен |
| SM-4 | Календарь отрисован | Месяц и год, 7×6 ячеек, прошедшие дни зачёркнуты |
| SM-5 | Слоты загружаются | Заголовок «Свободное время», слоты по группам, бейдж с числом |
| SM-6 | Сквозной позитивный сценарий | Выбор дня → слота → в панели дата и время → «Далее» активна |
| SM-7 | API отвечает | `GET /services`, `/masters`, `/slots` дают `200`, `/docs` открывается |

**Готовность к полному тестированию:** все 7 пунктов пройдены.
При падении SM-1 или SM-7 (страница не открывается, API недоступен)
тестирование блокируется и передаётся в разработку. При падении
SM-2…SM-6 — дефект фиксируется, полное тестирование продолжается,
если сломанный блок не блокирует остальные проверки.

Метрики посчитаны по формулам из лекции 4 и по фактическим прогонам.

| **Test Efficiency** (исследовательская сессия) | дефектов / затраченное время | 4 дефекта / 1,2 ч (70 мин) | **333%** | самые «дорогие» находки |

только те требования, которые успели записать, и поэтому целый пласт

### 3.6 Роли, процесс и коммуникация

Лекция 4: в маленькой команде без выделенного аналитика QA становится
«фильтром неоднозначности» и владельцем процесса качества.

| Роль | Кто в учебном проекте | Что делал |
|---|---|---|
| Проектировщик | автор макета Figma | макет на 6 экранов и 3 альтернативных, определение шагов записи |
| Фронтенд | `frontend-1…4` | вёрстка → нативный JS → React → React + сервер |
| Бэкенд | `backend-1…4` | Python → FastAPI → SQLAlchemy/Alembic → Pydantic |
| **QA** | Кондрашев Никита | тест-план, чек-лист, тест-кейсы, баг-репорты, матрица покрытия, реестр неоднозначностей, отчёт |

**Процесс на одной фиче** — на примере «выбор мастера» (по образцу
лекции с «оформлением заказа»):

1. Проектировщик обновляет макет: появляется экран 03 «Мастер»
   и четвёртый шаг в индикаторе.
2. QA сверяет макет с текущим списком требований и фиксирует
   неоднозначность **AMB-01** («три шага или четыре?»).
3. Трактовка согласуется, в `decomposition.md` появляются REQ-69…REQ-72.
4. Требования попадают в матрицу трассируемости — сразу видно,
   что покрытия нет.
5. QA пишет тест-кейсы TC-32…TC-34, проводит прогон, находит дефект
   и оформляет BUG-012.
6. Если реализация не успела — дефект остаётся открытым и попадает
   в отчёт с приоритетом Critical, а не растворяется в «непроверенном».

**Правила коммуникации:**

| Ситуация | Действие |
|---|---|
| Требование неоднозначно | запись в реестр AMB-NN + предложение трактовки |
| Изменился макет или API | короткое сообщение в чат со ссылкой на артефакт |
| Найден дефект | баг-репорт BUG-NN и строка в сводке |
| Дефект исправлен | ретест, статус «Исправлен, проверен» + номер теста |
| Прогон закончен | обновление статусов и краткий отчёт |

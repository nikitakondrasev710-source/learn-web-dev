## 0. Вход в тестирование, критерии завершения и структура отчёта

### 0.1 Smoke-проверка (7 пунктов)

Выполняется перед полным тестированием, занимает 10–15 минут.

| № | Проверка | Ожидаемый результат |
|---|---|---|
| SM-1 | Страница открывается, консоль браузера | Страница отрисована, ошибок в консоли нет |
| SM-2 | Шапка и подвал | Логотип, 4 пункта меню, телефон `tel:`, кнопка «Войти», копирайт |
| SM-3 | Индикатор шагов | Три шага, текущий «Дата и время» выделен |
| SM-4 | Календарь отрисован | Месяц и год, 7×6 ячеек, прошедшие дни зачёркнуты |
| SM-5 | Слоты загружаются | Заголовок «Свободное время», слоты по группам, бейдж с числом |
| SM-6 | Сквозной позитивный сценарий | Выбор дня → слота → в панели дата и время → «Далее» активна |
| SM-7 | API отвечает | `GET /services`, `/masters`, `/slots` дают `200`, `/docs` открывается |

**Готовность к полному тестированию:** все 7 пунктов пройдены.
При падении SM-1 или SM-7 (страница не открывается, API недоступен)
тестирование блокируется и передаётся в разработку. При падении
SM-2…SM-6 — дефект фиксируется, полное тестирование продолжается,
если сломанный блок не блокирует остальные проверки.

### 0.2 Критерии завершения тестирования

1. Выполнены 100% запланированных проверок: 37 пунктов чек-листа,
   31 тест-кейс и 64 проверки в автотестах
   (`check_api.py` — 35, `check_pydantic.py` — 29).
2. Все требования из [`decomposition.md`](decomposition.md) покрыты

4. Smoke-набор SM-1…SM-7 проходит на финальной сборке.
5. Отчёт о тестировании заполнен, баг-репорты p1 и p2 приложены.
6. Код проходит проверки артефактов: W3C — 0 замечаний,

### 0.3 Структура итогового отчёта

| Раздел | Что содержит |
|---|---|
| 1. Объект и объём | что тестировали, что вне объёма |
| 2. Подход | виды и уровни тестирования, инструменты |

## 7. Рекомендации

1. **Убрать захардкоженные даты.** Сейчас «сегодня» фиксировано
   (`2026-11-19`) — на реальной дате тесты будут падать.
   Нужно брать `new Date()` или данные с сервера.
2. **Добавить блокировку на уровне БД** при создании записи
   (BUG-008) — `SELECT ... FOR UPDATE` или уникальный индекс
   на `(master_id, starts_at)`.
3. **Покрыть автотестами UI** — Playwright или Cypress для сценария
   записи целиком, а не только API.
4. **Добавить CI** — GitHub Actions: линтер, тесты API, валидатор HTML
   на каждый push.
5. **Проверить на реальных устройствах** — iOS Safari, Android Chrome,
   так как сейчас адаптивность проверена только эмуляцией.
6. **Сделать эталонный макет** в Figma и автоматизировать
   визуальную сверку (скриншот-тесты).

ТЕСТИРОВАНИЕ. ЗАДАНИЕ 1. ВИДЫ ТЕСТИРОВАНИЯ И ТЕСТ-ПЛАН

Объект тестирования: веб-приложение барбершопа «БРИТВА».

Назначение приложения: предоставление клиенту возможности выбрать услугу, мастера, дату и время, а затем оформить запись на посещение.

Основной источник требований: макет Figma «БРИТВА — путь записи клиента».

1. ОБЩИЕ СВЕДЕНИЯ

1.1. Цель тестирования

Цель тестирования заключается в проверке соответствия веб-приложения требованиям, проверке корректности пользовательского интерфейса, бизнес-логики и взаимодействия с серверной частью.

В рамках тестирования необходимо проверить:

1. Работу основных экранов приложения.
2. Корректность переходов между этапами записи.
3. Выбор услуг и мастеров.
4. Работу календаря и выбор свободного времени.
5. Создание и отмену записей.
6. Проверку корректности вводимых данных.
7. Обработку ошибок сервера и сетевых соединений.
8. Адаптивность интерфейса.
9. Доступность элементов управления.
10. Соответствие приложения макету Figma.

1.2. Область тестирования

В область тестирования входят следующие функциональные модули.

Модуль 1. Главная страница.

Проверяются шапка сайта, логотип, навигация, информационные блоки, кнопка перехода к записи и подвал.

Модуль 2. Выбор услуги.

Проверяются отображение списка услуг, информация о стоимости и продолжительности, выбор услуги и переход к следующему этапу.

Модуль 3. Выбор мастера.

Проверяются отображение карточек мастеров, информация об их специализации, выбор мастера и переход к календарю.

Модуль 4. Календарь.

Проверяются отображение текущего месяца, переключение месяцев, выбор даты, блокировка прошедших дат и переход между годами.

Модуль 5. Свободное время.

Проверяются загрузка временных интервалов, отображение свободных и занятых слотов, выбор времени и обработка ошибок загрузки.

Модуль 6. Подтверждение записи.

Проверяются отображение информации о заказе, ввод контактных данных, проверка введённых значений и отправка запроса на создание записи.

Модуль 7. Экран успешной записи.

Проверяется отображение информации о созданной записи и доступность дальнейших действий.

Модуль 8. API.

Проверяются получение услуг, получение мастеров, получение свободных слотов, создание, получение, изменение и отмена записей.

2. ПОЛЬЗОВАТЕЛЬСКИЙ СЦЕНАРИЙ

2.1. Сценарий использования UC-01. Онлайн-запись клиента

Название сценария: оформление записи в барбершоп «БРИТВА».

Основной участник: клиент барбершопа.

Заинтересованные стороны: клиент и администрация барбершопа.

Цель: оформление записи на выбранную услугу к выбранному мастеру на определённую дату и время.

Триггер: клиент нажимает кнопку «Записаться» на главной странице сайта.

Предусловия:

1. Веб-приложение доступно для использования.
2. Серверная часть приложения запущена.
3. Доступен список услуг.
4. Доступен список мастеров.
5. Система может получать информацию о свободном времени.

Постусловия:

1. Запись создана и сохранена в системе.
2. Клиент получил подтверждение оформления записи.
3. Клиенту доступна информация об услуге, мастере, дате и времени посещения.

Основной поток событий:

1. Клиент открывает главную страницу барбершопа.
2. Клиент выбирает действие «Записаться».
3. Система открывает экран выбора услуги.
4. Клиент просматривает доступные услуги.
5. Клиент выбирает необходимую услугу.
6. Система сохраняет выбранную услугу и открывает экран выбора мастера.
7. Клиент просматривает доступных мастеров.
8. Клиент выбирает подходящего мастера.
9. Система сохраняет выбранного мастера и открывает календарь.
10. Клиент выбирает дату посещения.
11. Система получает информацию о свободных временных интервалах выбранного мастера.
12. Клиент выбирает подходящее время.
13. Система сохраняет выбранную дату и время.
14. Клиент переходит к подтверждению записи.
15. Система отображает итоговую информацию: услугу, мастера, дату, время и стоимость.
16. Клиент вводит необходимые контактные данные.
17. Клиент подтверждает запись.
18. Система проверяет корректность данных и доступность выбранного времени.
19. Система отправляет запрос на создание записи.
20. Сервер создаёт запись и возвращает результат операции.
21. Система отображает экран успешной записи с информацией о посещении.

Альтернативный поток событий AF-01. Некорректный номер телефона.

1. Клиент находится на экране подтверждения записи.
2. Клиент вводит номер телефона в неправильном формате.
3. Система проверяет формат введённого номера.
4. Система отображает сообщение об ошибке.
5. Поле с некорректным номером визуально выделяется.
6. Клиент исправляет введённые данные.
7. Клиент повторно подтверждает запись.

Результат: запись не отправляется до исправления некорректных данных.

Альтернативный поток событий AF-02. Выбранное время стало занятым.

1. Клиент выбирает свободный временной интервал.
2. До подтверждения записи выбранное время занимает другой клиент.
3. Клиент подтверждает запись.
4. Сервер обнаруживает пересечение записей.
5. Сервер возвращает ответ с кодом 409 Conflict.
6. Система сообщает клиенту, что выбранное время больше недоступно.
7. Система обновляет информацию о занятости временных интервалов.
8. Клиент выбирает другое доступное время.

Результат: запись на занятое время не создаётся.

Альтернативный поток событий AF-03. Ошибка сетевого соединения.

1. Клиент находится на экране подтверждения.
2. Клиент отправляет запрос на создание записи.
3. Во время отправки или обработки запроса возникает ошибка сетевого соединения.
4. Система сообщает о невозможности завершить операцию.
5. Клиенту предлагается повторить отправку запроса.
6. После восстановления соединения клиент повторяет операцию.
7. Система проверяет результат предыдущего запроса перед повторным созданием записи.

Результат: клиент получает информацию о состоянии записи. Повторная отправка не должна приводить к созданию дублирующей записи.

3. ИСТОЧНИКИ ТРЕБОВАНИЙ

При формировании требований используются следующие источники:

1. Макет Figma «БРИТВА — путь записи клиента». Используется для определения состава экранов, пользовательских переходов, визуальных элементов и состояний интерфейса.

2. Документация Frontend. Используется для определения требований к структуре страницы, компонентам, стилям и взаимодействию с пользователем.

3. Документация Backend. Используется для определения требований к API, обработке запросов, валидации данных и кодам HTTP-ответов.

4. Результаты тестирования. Используются для выявления дополнительных требований, необходимых для устранения обнаруженных дефектов.

При противоречии между макетом и реализацией приоритет имеет согласованная спецификация продукта. Само наличие функциональности в исходном коде не является подтверждением соответствия требованиям.

4. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

Формат регистрации требований:

Идентификатор: уникальный номер требования.
Наименование: краткое название проверяемой функции.
Описание: однозначное описание ожидаемого поведения системы.
Приоритет: степень важности требования.
Критерий приёмки: условие, при выполнении которого требование считается реализованным.
Источник: документ или материал, из которого получено требование.

4.1. Модуль M1. Каркас страницы

REQ-01

Наименование: отображение логотипа.

Описание: система должна отображать логотип барбершопа в шапке сайта. Логотип должен быть ссылкой на главную страницу.

Приоритет: средний.

Критерий приёмки: логотип отображается на всех основных экранах. При нажатии пользователь переходит на главную страницу.

Источник: макет Figma, документация Frontend.

REQ-02

Наименование: навигационное меню.

Описание: шапка сайта должна содержать четыре пункта навигации: «Услуги», «Мастера», «Отзывы», «Контакты».

Приоритет: средний.

Критерий приёмки: все четыре пункта отображаются и позволяют перейти к соответствующему разделу сайта.

Источник: макет Figma, документация Frontend.

REQ-03

Наименование: ссылка на телефон.

Описание: номер телефона в шапке сайта должен быть оформлен как ссылка с использованием протокола tel.

Приоритет: низкий.

Критерий приёмки: при нажатии на номер телефона браузер предлагает выполнить звонок на указанный номер.

Источник: документация Frontend.

REQ-04

Наименование: кнопка авторизации.

Описание: в шапке сайта должна отображаться кнопка «Войти».

Приоритет: низкий.

Критерий приёмки: кнопка отображается в шапке и доступна для взаимодействия.

Источник: документация Frontend.

REQ-05

Наименование: возврат к выбору услуги.

Описание: на последующих этапах оформления записи должна быть доступна навигация для возврата к выбору услуги.

Приоритет: средний.

Критерий приёмки: пользователь может вернуться к выбору услуги без необходимости повторного открытия приложения.

Источник: макет Figma.

REQ-06

Наименование: заголовок страницы.

Описание: каждый этап оформления записи должен содержать заголовок и подзаголовок, соответствующие текущему экрану.

Приоритет: средний.

Критерий приёмки: заголовок и подзаголовок соответствуют назначению открытого экрана.

Источник: макет Figma, документация Frontend.

REQ-07

Наименование: подвал сайта.

Описание: подвал должен содержать информацию об авторских правах, ссылку на политику конфиденциальности и правила записи.

Приоритет: низкий.

Критерий приёмки: все перечисленные элементы отображаются в нижней части страницы и имеют корректное содержание.

Источник: документация Frontend.

REQ-08

Наименование: адаптивная структура страницы.

Описание: интерфейс должен адаптироваться под ширину экрана пользователя.

Приоритет: высокий.

Критерий приёмки: на широких экранах основное содержимое отображается в двух колонках, на мобильных экранах колонки располагаются одна под другой. Горизонтальная прокрутка не появляется.

Источник: документация Frontend.

4.2. Модуль M2. Индикатор шагов

REQ-09

Наименование: отображение этапов записи.

Описание: индикатор должен содержать четыре этапа: «Услуга», «Мастер», «Дата и время», «Подтверждение».

Приоритет: высокий.

Критерий приёмки: все четыре этапа отображаются в правильной последовательности.

Источник: макет Figma.

REQ-10

Наименование: выделение текущего этапа.

Описание: текущий этап оформления записи должен визуально отличаться от остальных этапов.

Приоритет: средний.

Критерий приёмки: при переходе между этапами индикатор выделяет именно тот этап, который открыт пользователю.

Источник: документация Frontend.

REQ-11

Наименование: обозначение пройденных этапов.

Описание: завершённые этапы оформления записи должны иметь визуальное обозначение выполненного состояния.

Приоритет: средний.

Критерий приёмки: после перехода к следующему этапу предыдущий этап отмечается как выполненный.

Источник: документация Frontend.

4.3. Модуль M3. Календарь

REQ-12

Наименование: отображение месяца и года.

Описание: заголовок календаря должен содержать название отображаемого месяца и соответствующий год.

Приоритет: высокий.

Критерий приёмки: после открытия календаря отображается правильный месяц и год. При переключении месяца заголовок обновляется.

Источник: макет Figma.

REQ-13

Наименование: названия дней недели.

Описание: календарь должен отображать названия дней недели в последовательности от понедельника до воскресенья.

Приоритет: средний.

Критерий приёмки: названия дней недели расположены в правильной последовательности.

Источник: макет Figma.

REQ-14

Наименование: структура календарной сетки.

Описание: календарь должен содержать семь столбцов и шесть строк для отображения дней месяца.

Приоритет: средний.

Критерий приёмки: календарная сетка содержит 42 ячейки.

Источник: макет Figma.

REQ-15

Наименование: отображение дней соседних месяцев.

Описание: дни соседних месяцев должны визуально отличаться от дней текущего месяца и быть недоступными для выбора.

Приоритет: средний.

Критерий приёмки: дни соседних месяцев отображаются приглушённым цветом. Нажатие на них не изменяет выбранную дату.

Источник: макет Figma.

REQ-16

Наименование: блокировка прошедших дат.

Описание: календарь не должен разрешать выбор дат, которые находятся раньше текущей даты.

Приоритет: высокий.

Критерий приёмки: прошедшие даты визуально выделены как недоступные и не реагируют на нажатие.

Источник: макет Figma, документация Backend.

REQ-17

Наименование: выделение текущей даты.

Описание: текущая дата должна отличаться от остальных дат с помощью пунктирной рамки.

Приоритет: низкий.

Критерий приёмки: текущий день выделен пунктирной рамкой независимо от наличия выбранной даты.

Источник: макет Figma.

REQ-18

Наименование: выделение выбранной даты.

Описание: выбранный пользователем день должен иметь тёмный фон или другое предусмотренное макетом визуальное выделение.

Приоритет: средний.

Критерий приёмки: после выбора доступного дня он визуально выделяется. При выборе другого дня выделение переносится.

Источник: макет Figma.

REQ-19

Наименование: переключение на предыдущий месяц.

Описание: календарь должен содержать кнопку перехода к предыдущему месяцу.

Приоритет: средний.

Критерий приёмки: после нажатия отображается предыдущий месяц с правильным количеством дней и расположением календарной сетки.

Источник: макет Figma.

REQ-20

Наименование: переключение на следующий месяц.

Описание: календарь должен содержать кнопку перехода к следующему месяцу.

Приоритет: средний.

Критерий приёмки: после нажатия отображается следующий месяц с правильным количеством дней и расположением календарной сетки.

Источник: макет Figma.

REQ-21

Наименование: переход между годами.

Описание: календарь должен корректно переключать год при переходе с декабря на январь и с января на декабрь.

Приоритет: высокий.

Критерий приёмки: при переходе с декабря на январь год увеличивается на единицу. При обратном переходе год уменьшается на единицу.

Источник: макет Figma.

REQ-22

Наименование: изменение выбранной даты при переключении месяца.

Описание: после перехода в месяц, в котором ранее выбранная дата недоступна, система должна автоматически установить допустимое состояние выбора.

Приоритет: высокий.

Критерий приёмки: в календаре не остаётся выбранной прошедшая дата. При отсутствии доступных дат выбор снимается.

Источник: документация Frontend, результаты тестирования.

REQ-23

Наименование: легенда календаря.

Описание: рядом с календарём должна отображаться легенда, объясняющая обозначения текущей и выбранной даты.

Приоритет: низкий.

Критерий приёмки: отображаются обозначения «Выбранный день» и «Сегодня».

Источник: макет Figma.

REQ-24

Наименование: выбор доступной даты.

Описание: пользователь должен иметь возможность выбрать любую доступную дату в отображаемом месяце.

Приоритет: высокий.

Критерий приёмки: после нажатия на доступный день система сохраняет выбранную дату и обновляет связанные элементы интерфейса.

Источник: макет Figma.

REQ-25

Наименование: запрет выбора прошедшей даты.

Описание: система должна игнорировать попытку пользователя выбрать дату, которая находится раньше текущей даты.

Приоритет: высокий.

Критерий приёмки: после нажатия на прошедшую дату выбранная дата не изменяется.

Источник: макет Figma, документация Backend.

4.4. Модуль M4. Свободные временные интервалы

REQ-26

Наименование: заголовок блока свободного времени.

Описание: блок с доступными временными интервалами должен иметь заголовок «Свободное время».

REQ-51

Приоритет: высокий.

Критерий приёмки: при всех указанных разрешениях содержимое доступно, элементы управления не перекрываются и горизонтальная прокрутка не появляется.

Источник: документация Frontend.

REQ-52

Приоритет: средний.

Критерий приёмки: проверка через валидатор W3C не выявляет ошибок разметки.

REQ-53

Наименование: визуальная реакция интерактивных элементов.

Описание: интерактивные элементы должны визуально реагировать на наведение указателя и получение фокуса.

REQ-57

Наименование: получение информации о мастере.

Критерий приёмки: при передаче даты в неправильном формате возвращается код 400 и сообщение об ошибке.

Источник: макет Figma.

REQ-79

Наименование: обработка занятого времени.

Приоритет: критический.

Критерий приёмки: после получения ответа 409 Conflict отображается сообщение о занятости времени. Соответствующий слот помечается как недоступный. Пользователь может вернуться к выбору другого времени.

Наименование: обработка сетевой ошибки.

Приоритет: высокий.

Критерий приёмки: отображается сообщение «Запись не отправлена» или «Не удалось отправить». Доступна кнопка «Повторить» и возможность вернуться к выбору времени.

REQ-81

Наименование: корректность расчёта стоимости.

Приоритет: высокий.

Критерий приёмки: при изменении выбранной услуги отображаемая стоимость автоматически обновляется и совпадает с ценой услуги в каталоге.

Источник: макет Figma, документация Backend.

REQ-82

Наименование: получение отдельной записи.

Описание: сервер должен предоставлять GET-метод /appointments/{appointment_id} для получения информации об отдельной записи по её идентификатору.

Приоритет: средний.

Критерий приёмки: при существующем идентификаторе возвращается информация о записи с кодом 200. При отсутствии записи возвращается код 404.

Источник: документация Backend, задание 2.

5. ВИДЫ ТЕСТИРОВАНИЯ

5.1. По степени доступа к внутреннему устройству приложения

Тестирование методом чёрного ящика.

Проверяется поведение приложения через пользовательский интерфейс и HTTP API без анализа внутренней реализации.

Основной инструмент проверки: действия пользователя, запросы к API и анализ полученных ответов.

Тестирование методом серого ящика.

Проверяется поведение приложения с дополнительным использованием технической информации: логов сервера, структуры ответов API и состояния данных.

Данный подход применяется при поиске причин обнаруженных ошибок.

5.2. По уровню тестирования

Модульное тестирование.

Проверяются отдельные функции и компоненты: вычисление доступных временных интервалов, проверка дат, валидация входных данных и расчёт стоимости.

Интеграционное тестирование.

Проверяется взаимодействие между пользовательским интерфейсом, серверным API и хранилищем данных.

Системное тестирование.

Проверяется приложение в целом. Основное внимание уделяется полному процессу оформления записи от открытия главной страницы до получения подтверждения.

5.3. По цели проведения

Функциональное тестирование.

Проверяется выполнение всех функциональных требований и соответствие ожидаемому поведению.

Регрессионное тестирование.

Проводится после исправления дефектов для проверки того, что существующая функциональность продолжает работать корректно.

Smoke-тестирование.

Выполняется быстрая проверка основных функций приложения после запуска или установки новой версии.

Визуальное тестирование.

Проверяется соответствие интерфейса макету Figma: расположение элементов, цвета, шрифты, размеры и отступы.

Кросс-браузерное тестирование.

Проверяется корректность работы приложения в браузерах Google Chrome, Mozilla Firefox, Microsoft Edge и Safari при наличии соответствующей тестовой среды.

Адаптивное тестирование.

Проверяется корректность отображения интерфейса на устройствах с различными размерами экранов.

Тестирование удобства использования.

Проверяется понятность интерфейса, логичность последовательности действий и доступность основных функций.

Тестирование доступности.

Проверяются навигация с клавиатуры, доступные имена элементов, визуальный фокус и контрастность.

Тестирование производительности.

Проверяется время загрузки страниц, скорость получения свободных временных интервалов и время обработки основных запросов.

Базовое тестирование безопасности.

Проверяется серверная валидация входных данных и невозможность обхода основных ограничений путём отправки некорректных запросов напрямую к API.

Исследовательское тестирование.

Проводится без заранее подготовленного набора тест-кейсов. Тестировщик самостоятельно исследует приложение в пределах выбранной области, фиксирует необычное поведение и обнаруженные дефекты.

Результаты исследовательского тестирования фиксируются в отдельном протоколе.

5.4. По характеру проверяемых данных

Позитивное тестирование.

Проверяется работа приложения при передаче корректных данных и выполнении предусмотренных условий.

Негативное тестирование.

Проверяется поведение приложения при передаче некорректных данных, выборе недоступного времени и возникновении ошибок сервера или сети.

6. ЧТО НЕ ВХОДИТ В ОБЛАСТЬ ТЕСТИРОВАНИЯ

В рамках данного этапа не выполняются следующие виды работ:

1. Полноценное нагрузочное тестирование с большим количеством реальных пользователей.
2. Проверка платёжных операций, поскольку функциональность оплаты не входит в текущий объём приложения.
3. Полноценное тестирование на проникновение и аудит безопасности инфраструктуры.
4. Проверка работы внешних сервисов рассылки SMS и электронной почты, если их интеграция отсутствует.
5. Проверка реальной работы географических и картографических сервисов за пределами отображения предусмотренного интерфейсом компонента.

10. ПРИОРИТЕТЫ ДЕФЕКТОВ

Blocker.

Критический дефект, полностью блокирующий работу приложения или делающий невозможным выполнение основного пользовательского сценария.

Пример: приложение не запускается или невозможно создать запись.

Critical.

Дефект, нарушающий ключевую бизнес-функцию и создающий серьёзные последствия для пользователя.

Пример: система позволяет записаться на время, которое уже занято другим клиентом.

Major.

Дефект, из-за которого важная функция работает неправильно, но существует возможность завершить операцию альтернативным способом.

Пример: при смене даты не сбрасывается ранее выбранное время.

Minor.

Дефект, который не нарушает основные функции приложения, но ухудшает удобство использования или визуальное восприятие.

Пример: неправильные отступы у отдельных элементов интерфейса.

Trivial.

Незначительный дефект, не оказывающий существенного влияния на работу приложения.

Пример: опечатка в информационной подсказке.

11. РИСКИ ТЕСТИРОВАНИЯ

Риск 1. Использование фиксированной даты.

Если текущая дата задана в исходном коде как постоянное значение, календарь может отображать неправильную информацию после изменения реальной даты.

Способ снижения риска: использовать динамическую текущую дату и отдельные тестовые значения для проверки календаря.

Риск 2. Хранение данных в оперативной памяти.

После перезапуска Backend созданные записи теряются.

Способ снижения риска: перед каждым тестовым прогоном подготавливать необходимые тестовые данные.

Риск 3. Различия между макетом и Backend.

Названия услуг, их стоимость, продолжительность и список мастеров отличаются между макетом Figma и серверной частью.

Способ снижения риска: согласовать единый каталог услуг и мастеров перед выполнением сквозного тестирования.

Риск 4. Отсутствие отдельных экранов приложения.

Некоторые экраны, предусмотренные макетом, могут отсутствовать в реализованной версии.

Способ снижения риска: фиксировать отсутствующую функциональность как несоответствие требованиям и регистрировать соответствующие дефекты.

Риск 5. Несоответствие контактных данных API и интерфейса.

Макет предусматривает проверку номера телефона, однако схема запроса Backend должна отдельно проверяться на наличие поля для передачи контактного номера.

Способ снижения риска: согласовать структуру данных Frontend и Backend до выполнения сквозного тестирования.

Риск 6. Различия маршрутов API.

Frontend и Backend могут использовать разные адреса конечных точек и разные форматы данных.

Способ снижения риска: согласовать единый API-контракт и проверить интеграцию перед системным тестированием.

Риск 7. Повторная отправка запросов.

При нестабильном соединении повторная отправка запроса может привести к созданию дублирующей записи.

Способ снижения риска: предусмотреть защиту от повторной отправки и проверку результата предыдущего запроса.

# Тестирование. Задание 1 — Виды тестирования и тест-план

**Что тестируем:** веб-приложение «БРИТВА» — запись клиента.
По макету путь такой: главная → услуга → мастер → дата и время →
подтверждение → успех. И три ветки на случай проблем: неверный телефон,
слот заняли, упала сеть.

### 1.0 Как пользователь проходит запись

Сценарий составлен по макету Figma (шесть экранов и три альтернативных) —
основной источник требований для остальных разделов.

**Если всё хорошо**

| Шаг | Экран макета | Действие пользователя | Ожидаемый результат |
|---|---|---|---|
| 1 | 01 Главная | Нажимает «Записаться» | Переход на выбор услуги |
| 2 | 02 Услуги | Выбирает услугу («Мужская стрижка» 1 800 ₽ / 60 мин) | Услуга выделена, кнопка «Далее» активна |
| 3 | 03 Мастер | Выбирает мастера из карточек | Карточка выделена, подписана «выбран» |
| 4 | 04 Дата и время | Выбирает день в календаре | День выделен, подгружаются свободные слоты |
| 5 | 04 Дата и время | Выбирает слот (например, 12:00) | Слот выделен, в панели дата и время |
| 6 | 05 Подтверждение | Проверяет детали и нажимает «Подтвердить» | Запись создаётся |
| 7 | 06 Успех | Видит «Вы записаны» и детали записи | Можно закрыть или добавить в календарь |

**Если что-то пошло не так**

| ID | Ветка | Условие | Ожидаемый результат |
|---|---|---|---|
| ALT-1 | Ошибка телефона | Введён телефон неверного формата | Поле подсвечено, текст ошибки, отправка не происходит |
| ALT-2 | Слот заняли | Пользователь выбрал слот, который уже занят | Сообщение, слот помечен занятым, «Выбрать другое время» |
| ALT-3 | Ошибка сети | Запрос на создание записи не прошёл | Экран «Запись не отправлена», кнопка «Повторить» |

> **Фактическое состояние.** Проходимы только шаги 4–5. Экранов 1–3
> и 6–7 в коде нет, кнопка «Далее» на шаге 5 не работает
> (BUG-009, BUG-012).

## 2. Виды тестирования, которые применяем

### По степени доступа к коду

- **Чёрный ящик** — основной подход: проверяем поведение через интерфейс
  и HTTP API, не зная внутренней реализации.
- **Серый ящик** — просматриваем логи сервера и структуру ответов API,
  когда нужно понять причину ошибки.

### По уровню детализации

- **Модульное** — функции вычисления свободных слотов, валидация дат,
  подсчёт стоимости.
- **Интеграционное** — связка «frontend → API → база данных».
- **Системное** — сквозной сценарий записи целиком.

### По цели

- **Функциональное** — все требования из макета и ТЗ выполняются.
- **Регрессионное** — после правок старые сценарии не сломались.
- **Smoke** — быстрая проверка «приложение вообще открывается и работает».
- **UI/визуальное** — соответствие макету: цвета, шрифты, отступы.
- **Кросс-браузерное** — Chrome, Firefox, Edge, Safari.
- **Адаптивное** — 360, 768, 1024, 1440 px.
- **Usability** — понятность шагов, читаемость, контраст.
- **Доступность (a11y)** — навигация с клавиатуры, alt-тексты, контраст.
- **Производительность** — скорость загрузки и отклика слотов.
- **Безопасность (базово)** — валидация на сервере, а не только на клиенте.

- **Исследовательское (exploratory) и ad-hoc** — без чек-листа
  и тест-кейсов, по чартеру и таймбоксу. Проводится после формального
  прогона для поиска дефектов там, где требования не сформулированы.
  Протокол — `../testing-4-practice/exploratory-session.md`.

### По позитивности сценария

- **Позитивные** — корректные данные, ожидаемый успех.
- **Негативные** — неверные данные, ожидаемая ошибка с понятным сообщением.

## 3. Что НЕ входит в этот этап

- Нагрузочное тестирование с реальной нагрузкой (только имитация).
- Тестирование оплаты — оплата в приложении не реализована.
- Пентест и проверка защищённости инфраструктуры.

## 6. Критерии начала и окончания тестирования

**Начало:** сборка разворачивается, главная страница открывается,
API отвечает на `/docs`.

**Окончание:** все тест-кейсы выполнены, критичных и блокирующих
дефектов нет, функциональность соответствует макету.

Плюс, по итогам лекции 4:

- список требований сверен с макетом, расхождения оформлены как
  дефекты или требования;
- проведена хотя бы одна исследовательская сессия с протоколом;
- посчитаны Failure Rate и Test Efficiency.

## 7. Приоритеты дефектов

| Уровень | Описание | Пример |
|---|---|---|
| Blocker | сценарий невозможен | запись не создаётся совсем |
| Critical | ключевая функция сломана | можно записаться на занятое время |
| Critical | объём меньше макета, сквозной сценарий не проходим | нет шага выбора мастера (BUG-012) |
| Major | функция работает неверно | не сбрасывается время при смене дня |
| Minor | косметический дефект | неверный отступ у кнопки |
| Trivial | незаметная мелочь | опечатка в подсказке |

## 8. Риски

1. Слоты и «сегодня» захардкожены — тесты зависят от даты запуска.
2. Данные хранятся в памяти/локальной БД — после перезапуска состояние теряется.
3. ~~Макет недоступен как эталон~~ — **снят 22.11.2026**: макет получен
   (6 экранов и 3 альтернативных), используется как основной источник
   требований. Обратный риск: реализация отстаёт от макета (BUG-012).
4. «Сегодня» в приложении захардкожено, тесты зависят от константы
   `17.10.2026`, а не от реальной даты (BUG-010).
5. Список требований может не совпадать с макетом, и это видно только
   при сверке. Поэтому в критерии окончания добавил обязательную
   сверку с макетом.

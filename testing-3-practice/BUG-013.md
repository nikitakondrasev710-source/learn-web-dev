BUG-013. Не реализована обработка ситуации, когда выбранное время стало занятым

Идентификатор: BUG-013
Заголовок: После того как выбранный интервал занял другой клиент, интерфейс не сообщает о конфликте и не предлагает выбрать другое время.
Приоритет: Major
Серьёзность: Высокая
Статус: Открыт

Окружение:
Операционная система: Windows 11.
Браузер: Google Chrome.
Frontend: frontend-4-practice, http://localhost:3000.
Backend: backend-2-practice, http://127.0.0.1:8000.
Компонент: подтверждение записи и обработка ответа POST /appointments.

Связанный Use Case: UC-01.
Альтернативный сценарий: ALT-02 — выбранное время стало занятым.
Связанный тест-кейс: TC-02.
Связанные требования: REQ-61, REQ-79.
Связанные дефекты: BUG-009, BUG-012.

Предусловия:
1. Frontend и Backend запущены.
2. Клиент загрузил свободные интервалы выбранного мастера на выбранную дату.
3. Интервал 10:30 первоначально отображается свободным.
4. До подтверждения первой записи другой клиент создаёт запись на тот же интервал для того же мастера.

Тестовые данные:
Дата: 10 декабря 2026 года.
Мастер: идентификатор 1.
Услуга: идентификатор 1.
Время начала: 10:30.
Продолжительность услуги: 60 минут.

Шаги воспроизведения:
1. Открыть страницу выбора даты и времени.
2. Загрузить интервалы для мастера 1 на 10 декабря 2026 года.
3. Убедиться, что интервал 10:30 отображается свободным.
4. Отправить через Backend запрос POST /appointments для создания первой записи мастера 1 на 10 декабря 2026 года в 10:30.
5. Убедиться, что Backend создал запись и вернул HTTP 201 Created.
6. Вернуться к странице первого клиента, где интервал 10:30 был загружен до создания второй записи.
7. Попытаться перейти к подтверждению записи на интервал 10:30.
8. Проверить, отправляется ли запрос на создание записи и как интерфейс отображает конфликт.

Ожидаемый результат:
1. Backend обнаруживает пересечение временных интервалов и возвращает HTTP 409 Conflict.
2. Повторная запись не создаётся.
3. Интерфейс отображает сообщение о том, что выбранное время уже занято.
4. Слот 10:30 помечается как недоступный.
5. Пользователю доступно действие «Выбрать другое время».
6. После обновления данных пользователь видит актуальные свободные интервалы.

Фактический результат:
Пользовательский путь до подтверждения записи в текущей реализации недоступен. Кнопка «Далее» не выполняет переход, экран подтверждения и отправка POST /appointments из интерфейса отсутствуют. Экран альтернативного сценария ALT-02 и обработка HTTP 409 на стороне Frontend не реализованы.

Причина:
Не завершён сквозной пользовательский путь. Backend может проверять пересечение записей, но Frontend не доводит пользователя до отправки запроса и не отображает альтернативное состояние при конфликте.

Влияние:
Клиент не получает понятного сообщения о том, что выбранное время стало недоступным, и не может продолжить оформление с другим временем.

Рекомендация по исправлению:
1. Реализовать переход к экрану подтверждения после выбора даты и времени.
2. Передавать данные записи в Backend через POST /appointments.
3. Обрабатывать HTTP 409 Conflict отдельно от остальных ошибок.
4. При получении HTTP 409 отображать сообщение о занятости времени.
5. Обновлять список временных интервалов.
6. Предоставлять пользователю действие «Выбрать другое время».

Критерии повторной проверки:
1. TC-02 выполняется через пользовательский интерфейс.
2. Backend возвращает HTTP 409 Conflict при пересечении записей.
3. Дублирующая запись не создаётся.
4. Пользователь видит сообщение о конфликте и может выбрать другое время.
5. После выбора другого свободного интервала запись успешно создаётся.

Примечание:
BUG-013 фиксирует отсутствие обработки альтернативного сценария ALT-02. Он связан с BUG-009 и BUG-012, но отдельно описывает требуемую реакцию интерфейса на HTTP 409 Conflict. До реализации экрана подтверждения фактическую обработку конфликта через пользовательский интерфейс проверить невозможно.
